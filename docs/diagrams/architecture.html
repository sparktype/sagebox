secretbox 현재 구현

에이전트가 MCP 서버를 띄울 때만 비밀을 환경변수로 주입하는 로컬 데몬입니다. 볼트(SBX2), 관리 CLI, Unix 데몬과 exec까지 구현된 상태를 세 장으로 나눠 그렸습니다.

01 · Architecture · trust boundary

구성 요소와 신뢰 경계

관리 CLI는 데몬을 거치지 않고 패스프레이즈로 볼트를 직접 고칩니다. 그래서 세션이 풀려 있어도 에이전트는 정책을 바꿀 수 없습니다. 에이전트가 고를 수 있는 것은 프로필 이름뿐이고, 명령(argv)은 볼트 안의 프로필에 고정돼 있습니다. execve 이후에는 같은 프로세스가 MCP 서버가 되어 에이전트와 stdio로 대화합니다. 비밀은 그 프로세스의 환경변수에만 존재합니다. 같은 UID 안의 악의적인 프로세스는 격리하지 않습니다(SPEC.md의 위협 모델 참고). 프로젝트별 네임스페이스를 쓰면 이 그림 전체(데몬, 볼트, 감사 로그)가 ~/.secretbox/ns/<name>/마다 한 벌씩 따로 존재하므로, 한 프로젝트를 풀어도 다른 프로젝트는 잠긴 채로 남습니다.

02 · Sequence · unlock → exec

세션 잠금 해제부터 execve까지

데몬은 첫 exec나 unlock에서 자동으로 뜹니다. 잠겨 있으면 exec가 GUI 대화상자로 패스프레이즈를 묻습니다. exec 연결은 응답 뒤에도 닫지 않습니다. 클라이언트가 그 소켓을 물려준 채 execve하므로, MCP 서버가 살아 있는 동안이 곧 임대 기간입니다. 마지막 임대가 끝나고 30초가 지나거나 8시간이 되면 데몬은 DEK를 지우고 종료합니다. 감사 로그를 쓰지 못하면 ARGV + ENV를 보내지 않습니다.

03 · Layer stack · envelope encryption

볼트 봉투 형식 (SBX2)

슬롯은 모두 32바이트 KEK를 얻어 같은 DEK를 푸는 방식이라, 하드웨어 슬롯을 추가해도 본문은 다시 암호화하지 않습니다. 모르는 kind의 슬롯은 해석하지 않고 그대로 보존합니다. 그래서 macOS에서 추가한 슬롯이 Linux에서 저장할 때 지워지지 않습니다. 패스프레이즈 슬롯은 항상 존재하며 복구 경로 역할을 합니다.
